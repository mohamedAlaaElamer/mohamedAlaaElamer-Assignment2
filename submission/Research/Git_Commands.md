# أوامر Git المهمة

## 1. `git squash`

**المعنى:**  
دمج مجموعة من الـ **commits** الصغيرة في **commit واحد** قبل عمل merge.

**سيناريو:**  
وأنت شغال على Feature معينة، بتعمل commits كتير مثل:

- `fix typo`
- `try again`
- `final fix`

قبل ما تفتح Pull Request، بتعمل **squash** للـ commits دي في commit واحد نظيف بعنوان واضح، عشان الـ **history** يبقى مرتب وسهل المراجعة من الـ reviewer.

---

## 2. `git merge` vs `git rebase`

الاتنين طرق لدمج التغييرات من Branch إلى Branch تاني، لكن كل واحد له فلسفة مختلفة.

### `git merge`

بيحافظ على الـ **history** كامل، وبيعمل **merge commit** بيربط الفرعين.

### `git rebase`

بياخد الـ commits بتاعتك ويعيد تطبيقها فوق آخر نسخة من الـ branch التاني، وبالتالي بيديك **history خطي** بدون merge commits إضافية.

**سيناريو:**  
في فريق شغال بنظام **Git Flow**، لما تخلص Feature Branch ممكن تعمل **merge** إلى `main` عشان تحافظ على تاريخ الفريق كامل.

أما لو أنت لوحدك شغال على Feature Branch وعايز تحدّثها بآخر تغييرات موجودة في `main` قبل ما تفتح Pull Request، ممكن تعمل **rebase** عشان الـ history يبقى أنظف وبدون commits دمج إضافية.

---

## 3. `git help`

**المعنى:**  
بيعرضلك شرح وتوثيق لأي أمر من أوامر Git.

**سيناريو:**  
نسيت الـ syntax بتاع أمر معين أو مش متذكر الـ flags المتاحة.

بدل ما تدور على الإنترنت، تقدر تستخدم:

```bash
git help <command>
```

وهتلاقي الشرح والتفاصيل الخاصة بالأمر.

---

## 4. `git cherry-pick`

**المعنى:**  
بياخد **commit واحد محدد** من Branch وينقله إلى Branch تاني.

**سيناريو:**  
لقيت إن فيه **Hotfix** اتعمل على Branch تاني، وأنت محتاج نفس الإصلاح في الـ Branch بتاعك، لكن مش عايز تدمج كل التغييرات الموجودة في الـ Branch التاني.

في الحالة دي تستخدم `cherry-pick` للـ commit المطلوب فقط.

---

## 5. `git clean`

**المعنى:**  
بيمسح الملفات اللي **مش متابعة (Untracked)** من الـ Working Directory.

**سيناريو:**  
بعد تجربة Build أو تشغيل Script، اتولدت ملفات مؤقتة كتير ومش محتاجها.

تقدر تستخدم:

```bash
git clean -fd
```

عشان تنضف المجلد من الملفات الـ Untracked.

---

## 6. `git grep`

**المعنى:**  
بيدور على نص معين داخل الملفات المتابعة في الـ Repository.

**سيناريو:**  
عايز تعرف كل الأماكن اللي بتستخدم فيها Function أو Variable معينة في المشروع.

بدل ما تفتح كل ملف يدويًا، تستخدم:

```bash
git grep "functionName"
```

وGit هيعرضلك الأماكن اللي ظهر فيها النص.

---

## 7. `git blame`

**المعنى:**  
بيوريك مين آخر شخص عدّل كل سطر في ملف، ومتى، وفي أي Commit.

**سيناريو:**  
لقيت سطر كود فيه Bug غريب ومش فاهم ليه اتكتب بالشكل ده.

تستخدم:

```bash
git blame filename
```

عشان تعرف:

- مين عدّل السطر.
- إمتى اتعدل.
- الـ Commit اللي حصل فيه التعديل.

وبعد كده تقدر ترجع للـ Commit وتشوف السياق اللي اتكتب فيه الكود.

---

## 8. `git bisect`

**المعنى:**  
بيستخدم **Binary Search** عشان يحدد الـ Commit اللي تسبب في ظهور Bug.

**سيناريو:**  
المشروع كان شغال كويس الأسبوع اللي فات، ودلوقتي ظهر Bug، لكن مش عارف المشكلة بدأت في أي Commit.

بدل ما تراجع مئات الـ commits واحد واحد، تستخدم:

```bash
git bisect
```

وتحدد لـ Git:

- Commit قديم شغال **Good**
- Commit جديد فيه المشكلة **Bad**

وGit هيبدأ يختبر الـ commits في المنتصف، لحد ما يحدد الـ Commit المسبب للمشكلة.

---

## 9. `git shortlog`

**المعنى:**  
بيلخص الـ commits ويجمعها حسب الـ **Author**.

**سيناريو:**  
عايز تعمل تقرير سريع يوضح كل عضو في الفريق ساهم بكام Commit.

تقدر تستخدم:

```bash
git shortlog -sn
```

عشان تحصل على إحصائية بعدد الـ commits لكل Author.

---

## 10. `git prune`

**المعنى:**  
بيمسح الـ **Objects** اللي مش مرتبطة بأي Commit أو Branch ومبقاش لها استخدام.

**سيناريو:**  
بعد ما تمسح Branches قديمة كتير، ممكن يفضل فيه Objects يتيمة داخل الـ Repository وتاخد مساحة.

في بعض الحالات يتم استخدام:

```bash
git prune
```

وغالبًا بيكون مرتبط بعملية:

```bash
git gc
```

لتنظيف الـ Repository وتقليل حجمه.

---

## 11. `git worktree`

**المعنى:**  
بيسمحلك تعمل أكتر من **Working Directory** لنفس الـ Repository، بحيث كل Directory يكون على Branch مختلف.

**سيناريو:**  
أنت شغال على Feature Branch وفجأة محتاج تعمل Hotfix عاجل على `main`.

بدل ما تعمل:

```bash
git stash
```

وتبدّل الـ Branch، ممكن تستخدم:

```bash
git worktree add
```

وتعمل مجلد تاني منفصل شغال على `main`.

وبكده تقدر تشتغل على الـ Hotfix وفي نفس الوقت تسيب شغلك الحالي زي ما هو بدون ما تلمسه.

---

## 12. `git verify-commit`

**المعنى:**  
بيتأكد إن الـ Commit موقّع **Signed** باستخدام مفتاح GPG صحيح.

**سيناريو:**  
في مشروع Open Source أو بيئة عمل بتطلب توثيق هوية المطورين، ممكن تستخدم:

```bash
git verify-commit <commit>
```

عشان تتأكد إن الـ Commit موقّع بشكل صحيح.

---

## 13. `git filter-repo`

**المعنى:**  
أداة قوية لإعادة كتابة تاريخ الـ Repository بالكامل.

ممكن تستخدمها في حالات مثل:

- حذف ملف من الـ History.
- إزالة API Key تم رفعه بالخطأ.
- إزالة معلومات حساسة من الـ Repository.
- تنظيف الـ History القديم.

**سيناريو:**  
اكتشفت إن ملف فيه **API Key** أو معلومات حساسة اتعمله Commit بالغلط من فترة طويلة.

حذف الملف من آخر Commit فقط مش كفاية، لأنه ممكن يفضل موجود في الـ Git History.

هنا ممكن تستخدم:

```bash
git filter-repo
```

لإعادة كتابة الـ History وإزالة البيانات المطلوبة من تاريخ الـ Repository.
